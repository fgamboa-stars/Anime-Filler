# Episode classifier

Predicts whether each newly imported anime episode is Canon, Mixed, Filler, Anime Canon, OVA, Special or Movie, explains why, and learns from human corrections.

The site stays static. This is a separate service with its own database, and its only link to the site is `cli export`, which writes the same dataset files the CSV importer does. The site's build and hosting don't change.

```
 AniList ──► import ──► episodes ──► classifyEpisode() ──► decision ──┬─ over 90%  auto-approved
                                          ▲                           ├─ 70-90%    suggested
                                          │                           └─ under 70% needs review
                                     evidence                                      │
                 rules · similar episodes · nearby episodes                        ▼
                 series profile · tag patterns                                human review
                                          ▲                                        │
                                          └──────────── learning ◄─────────────────┘
                                                                                   │
                                          site dataset files ◄── cli export ◄──────┘
```

## How well it works

[docs/BACKTEST.md](docs/BACKTEST.md) has the full results, regenerated by `npm run backtest`. It replays 7,045 curated labels as if each episode were new. In short:

- **It's good when nearby episodes have been reviewed**, and much weaker without them.
- **With no trusted labels in a series, it can't tell filler apart using AniList data.** New series and new seasons score about the same as always guessing canon, because AniList has no per-episode information beyond a streaming title. The system knows this and sends those episodes to a person instead of auto-approving them.

- **Sparse review pays off.** Reviewing one episode in eight lifts accuracy on the rest from 70% to 79%, and auto-approved predictions in that scenario were right 92% of the time.

So the system saves the most review time on long-running shows, where each reviewed episode makes the next easier to classify.

### What each layer contributes

Accuracy / macro F1 with one layer removed, measured on 2026-11-03:

| Configuration | Next episode | Sparse review | Batch tail |
| --- | ---: | ---: | ---: |
| All layers | 84.2 / 73.9 | 79.3 / 68.1 | 69.2 / 46.8 |
| Without arc | 68.4 / 20.5 | 70.1 / 20.7 | 65.1 / 19.8 |
| Without series | 84.9 / 74.8 | 79.7 / 66.8 | 67.5 / 32.0 |
| Without similarity | 84.1 / 73.9 | 79.0 / 68.0 | 69.6 / 48.1 |
| Without tags | 84.2 / 74.0 | 79.3 / 67.9 | 69.2 / 46.8 |
| Without rules | 84.3 / 74.3 | 79.2 / 68.1 | 70.0 / 48.4 |

Nearby episodes do nearly all the work. The series profile mainly helps when nothing nearby is reviewed. Similarity, tags and rules make little measurable difference on this catalog. Rules are still needed for what the labels can't measure: OVA, Special, Movie and recaps. Similarity and tag patterns are what would benefit if richer episode text became available.

A semantic embedding model (all-MiniLM-L6-v2) scored the same as the built-in feature hashing, within 0.2 points in every scenario, so the service uses hashing. It needs no model download or GPU. That comparison ran before the final rule adjustments, which don't affect similarity.

The weights differ from the 40/30/20/10 split in the original brief for this reason: they follow what the backtest measured. They live in `engine_settings`.

## Quick start

No Postgres needed. PGlite runs real Postgres with pgvector in-process:

```bash
cd classifier
npm install
export DATABASE_URL=pglite:./.pgdata
export API_TOKENS="$USER:admin:$(openssl rand -hex 32)"

npm run cli -- seed              # load the site's datasets as curated history
npm run cli -- import 154587     # import and classify one anime from AniList
npm run dev                      # API on :3000
```

For production, point `DATABASE_URL` at Postgres with the `vector` extension. Use a direct connection, not a pooler such as PgBouncer: the service sets `hnsw.ef_search` as a startup parameter, which poolers commonly reject.

To run the whole stack in Docker, with separate API and worker containers and a real Postgres, from the repo root:

```bash
export POSTGRES_PASSWORD=$(openssl rand -hex 16)
export API_TOKENS="$USER:admin:$(openssl rand -hex 32)"
docker compose -f classifier/docker-compose.yml up --build -d
docker compose -f classifier/docker-compose.yml exec api node dist/cli.js seed
```

`npm test` uses the in-process database. To include the tests that need true concurrency, point the suite at a throwaway Postgres. It creates and drops its own databases:

```bash
docker run -d --name classifier-test-pg -e POSTGRES_PASSWORD=test -p 127.0.0.1:55432:5432 pgvector/pgvector:pg17 -c max_connections=300
TEST_POSTGRES_URL=postgres://postgres:test@127.0.0.1:55432/postgres npm test
```

| Command | Purpose |
| --- | --- |
| `npm test` | All tests, using real SQL on in-process Postgres |
| `npm run backtest` | Replay the datasets, refit calibration, rewrite `docs/BACKTEST.md` |
| `npm run cli -- seed` | Load datasets and activate the fitted calibration |
| `npm run cli -- import <id>` | Import and classify one anime now |
| `npm run cli -- reclassify <id>` | Re-run the engine on a series' unreviewed episodes |
| `npm run cli -- rebuild-learning` | Regenerate everything learned from labels |
| `npm run cli -- stats [YYYY-MM]` | Monthly statistics |
| `npm run cli -- export <id> [--dry-run]` | Write a site dataset. Then run `npm run data:index` at the repo root |

## How a prediction is made

`classifyEpisode()` is the only thing the rest of the service knows about. The current engine is `HybridEngine` in [src/engine/hybrid.ts](src/engine/hybrid.ts). Five layers each give an opinion:

| Layer | Evidence | File |
| --- | --- | --- |
| Rules | Weighted rules stored in the database | [rules.ts](src/engine/rules.ts) |
| Similarity | The 20 nearest classified episodes, by embedding | [similarity.ts](src/engine/similarity.ts) |
| Arc | Nearby episodes in this series, weighted by distance and trust | [arc.ts](src/engine/arc.ts) |
| Series | This series' label mix, or its earlier seasons' for a new season | [series.ts](src/engine/series.ts) |
| Tags | Learned P(category given tag), series-level and episode-level | [tags.ts](src/engine/tags.ts) |

**Combining them.** Each layer's opinion is compared with the base rate, and the differences are added as log-odds. A layer that always says "canon" on a catalog that's 70% canon therefore adds nothing, while strong local evidence can outvote the base rate. Thin evidence pulls a layer toward no opinion.

**Rules.** Points add directly to a category's log-odds, scaled by the rule's learned skill: how much better than the base rate it has actually done. `score_value` is never changed by the system. On this catalog "Manga Adaptation" earns almost no skill, because 94% of the shows are manga adaptations, so it can't tell episodes apart. Rules marked `decisive` state a fact, such as AniList's format being `MOVIE`, and settle the result outright.

**Confidence.** The raw score goes through a calibration curve fitted by the backtest, so a stated 94% means about 94% of such predictions were right. There's a separate curve per evidence tier, because the same score means different things depending on how close the nearest trusted labels are:

| Tier | Nearest trusted labels |
| --- | --- |
| `bracketed` | Within 6 episodes on both sides |
| `adjacent` | Within 6 episodes on one side |
| `series` | Elsewhere in the series, or in a related season |
| `none` | Nowhere |

Only `bracketed` and `adjacent` may auto-approve; the others are held at 90%, so a new season always gets a person's attention. In the backtest, predictions for new seasons that reached auto-approve confidence were right only 41% of the time. A score with no fitted curve is capped at 85%.

**Trust and anti-drift.**

| Trust | Source | Weight as evidence |
| --- | --- | --- |
| High | A human reviewed it | 1.0 |
| Medium | Curated dataset label, imported rather than reviewed | 0.6 |
| Low | The system's own prediction, including auto-approved ones | 0.1 |

Low-trust examples can't reach other series: the cross-series vector index only contains High and Medium. They never enter tag patterns, rule stats or the base rate, and never lift an episode's evidence tier. A chain of predictions therefore can't vouch for itself into auto-approval.

**Reviewed records are protected by the database.** A trigger rejects any change to a reviewed episode unless it comes with a new human classification, whatever code path attempts it. `classification_history` and `review_audit_log` reject updates and deletes.

## What happens on a review

In one transaction: the decision, its audit record, updated tag patterns and base rate, updated rule stats, the recalculated series profile and detected arcs, and a queued re-classification of the series' unreviewed episodes. Corrections to corrections reverse the earlier count first, and a test confirms the incremental result matches a full rebuild.

## API

Everything under `/v1` needs `Authorization: Bearer <token>`. Tokens come from `API_TOKENS`, and with none set every request gets a 401. The reviewer in the audit log is the token's name and can't be supplied in the request.

| Method and path | Role | Purpose |
| --- | --- | --- |
| `POST /v1/imports` | admin | Queue an AniList import. Returns a job id |
| `GET /v1/jobs/:id` | reader | Job status and result |
| `POST /v1/classify` | reader | Dry run for a described episode. Stores nothing |
| `GET /v1/anime/:id/episodes` | reader | List, filter by `category` or `tag`, page with `after` |
| `GET /v1/anime/:id/episodes/:n/classification` | reader | The full explanation |
| `GET /v1/anime/:id/profile` | reader | Series profile |
| `GET /v1/anime/:id/arcs` | reader | Detected runs |
| `GET /v1/review-queue` | reader | Predictions waiting on a person, by `decision` |
| `POST /v1/episodes/:id/review` | admin | Approve or override |
| `POST /v1/episodes/:id/tags` | admin | Add a tag AniList can't provide, such as `anime-original` |
| `GET /v1/episodes/:id/history` | reader | Every classification and review |
| `GET /v1/rules` | reader | Rules with their outcome stats |
| `POST /v1/rules`, `PATCH /v1/rules/:id` | admin | Add or edit rules |
| `GET /v1/stats/monthly?month=YYYY-MM` | reader | Accuracy by rule, layer and series, plus corrections |
| `GET /healthz`, `GET /readyz` | none | Liveness and readiness |
| `GET /metrics` | reader | Prometheus metrics |

Abridged classification response:

```json
{
  "episode": 25,
  "prediction": "Filler",
  "category": "FILLER",
  "confidence": 94,
  "decision": "AUTO_APPROVED",
  "evidenceTier": "bracketed",
  "reasons": ["Located inside Filler run, episodes 21-30", "Series profile indicates 19% Filler probability"],
  "similarEpisodes": [
    {
      "episode": 22,
      "classification": "Filler",
      "similarity": 0.92,
      "trust": "MEDIUM",
      "selectedBecause": "Title and metadata 92% similar; same series; curated label"
    }
  ],
  "contributors": [{ "name": "arc", "evidenceShare": 71, "strength": 0.99, "leans": "Filler", "reasons": ["..."] }],
  "review": { "status": "UNREVIEWED", "history": [] },
  "engine": { "name": "hybrid", "version": "1.0.0" }
}
```

To review:

```bash
curl -X POST localhost:3000/v1/episodes/123/review \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"action":"OVERRIDE","category":"MIXED","reason":"Second half adapts chapter 40"}'
```

An override needs a `category` and a `reason`. Sending `expectedClassificationId` returns a 409 if someone else changed the episode first.

## Adding a rule

Rules are data. A condition can combine `all`, `any` and `not` over `in`, `matches` (case-insensitive regex), `gte` and `lte`, on any of the fields in [src/domain/rules.ts](src/domain/rules.ts).

```bash
curl -X POST localhost:3000/v1/rules -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' -d '{
  "ruleName": "Clip Show",
  "targetCategory": "SPECIAL",
  "scoreValue": 40,
  "condition": { "field": "episode.title", "matches": "\\bclip show\\b" },
  "explanation": "Title calls itself a clip show"
}'
```

Episode-level tags come from `tag_detectors`, or from `POST /v1/episodes/:id/tags`. The rules "Anime Original" and "Original Character" stay idle until episodes carry those tags, because AniList has no such data per episode.

## Replacing the engine

Implement `ClassifierEngine` from [src/engine/classifier.ts](src/engine/classifier.ts), register it in [src/container.ts](src/container.ts), and set `CLASSIFIER_ENGINE`. The API, storage, review flow and export all work against that interface, and a test swaps in a stub engine to prove it. To change the embedding model, implement `Embedder`, keep 384 dimensions or add a migration, then re-run `seed`. Stored vectors are hashed by model, so they regenerate on their own.

Before switching, run the backtest against the new engine. It's the same replay either way, and it refits the calibration.

## Keeping confidence honest

Rerun `npm run backtest` and `npm run cli -- seed` when the catalog grows noticeably or the engine or its settings change. Calibration is tied to how the engine scores, so a stale curve quietly makes the bands wrong. Watch the monthly `byDecision` figures: if reviewers correct auto-approved episodes more than about 1 time in 10, raise `thresholds.autoApprove` in `engine_settings`.

## Performance

Measured on 2026-11-03 with 307,045 episodes on Postgres 17 and pgvector 0.8, in Docker Desktop on a laptop (8 CPUs, 8 GB):

| Operation | Time |
| --- | ---: |
| Classify one episode, all evidence included | p50 9 ms, p95 13 ms |
| Similar-episode search | p50 10 ms, p95 15 ms |
| Review, including all learning | p50 29 ms, p95 37 ms |
| Episode lookup | p50 under 1 ms |
| Review queue page | p50 2 ms |
| Import and classify a new 1,000-episode series | 21 s |
| The same series again, all cached | 0.8 s |
| Monthly statistics | 0.1 s |
| Rebuild all learning | 42 s |
| Build the vector index on 240,000 episodes | about 70 s |

Search quality was measured separately, on 247,000 vectors built from the catalog's real title vocabulary: the index finds 93% of the true 20 nearest episodes, and their similarity is 99.3% of an exact scan.

These are optimistic in three ways. Requests ran one at a time, not concurrently. The database was in memory, so disk speed played no part. And most episodes were synthetic, with little review history behind them. Expect real numbers to be somewhat slower, though this leaves plenty of headroom.

When loading a large catalog, drop the vector index first and recreate it afterwards. Building it once is far faster than updating it per row.
